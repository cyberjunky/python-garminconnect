# SPEC-002: Distribución equilibrada y responsive de Tri-Coach

## 1. Problema y valor

El usuario reporta que la aplicación se muestra concentrada a la izquierda en Safari. La regla actual de ancho máximo y margen cero es compatible con ese resultado. Se busca una distribución equilibrada del dashboard dentro del espacio disponible junto a la navegación, con controles utilizables en todos los anchos acordados. El chat conserva su composición independiente.

## 2. Alcance

### No incluye (no-objetivos)

- Rediseñar marca, colores, tipografía, jerarquía de tarjetas o contenidos de entrenamiento.
- Cambiar APIs, cálculos, autenticación, collector, workflows, esquemas, credenciales o datos persistentes.
- Añadir dependencias, framework de pruebas, modo demo de producto o migrar arquitectura.
- Centrar cada burbuja del chat: se conserva la alineación por rol.
- Resolver deudas Python/arquitectura de T-0017/T-0020 o volver a auditar todos los criterios históricos de T-0014.
- Probar producción con envíos de chat, actualizar Garmin o publicar capturas con información personal.
- Afirmar compatibilidad iOS por una ventana estrecha de Safari macOS. No se incluye una certificación específica de teclado virtual iOS.

### Incluye

- Contenedor común de `/`, `/retos`, `/mesociclos`, `/70-3-cartagena`.
- Responsive y prevención de recortes producidos por el layout en esas rutas y `/chat?conversation=layout-synthetic`.
- Prueba de navegación y controles existentes con respuestas sintéticas, sin persistencia.
- Evidencia antes/después en Safari real, comprobación independiente y metadatos SemVer.

## 3. Historias de usuario

- HU-1: Como usuario, quiero aprovechar el área disponible junto al menú para leer el dashboard con márgenes equilibrados.
- HU-2: Como usuario en una ventana estrecha, quiero llegar a cada control sin desplazamiento horizontal de toda la página.
- HU-3: Como usuario del coach, quiero conservar navegación, historial y composición del chat después del ajuste de estilos.

### Geometría G (píxeles CSS, zoom 100%)

Medir el rectángulo de `.app-main` (`A`, ancho disponible) y el `main` hijo (`W`, caja con padding). No centrar respecto al viewport completo cuando existe sidebar.

- Para `viewport > 800`: `W = min(A,1120)`, padding lateral `P = 28`; diferencia entre ambos márgenes exteriores de `main` ≤2px.
- Para `viewport <= 800`: `W = A`, `P = 16`; diferencia de márgenes exteriores ≤2px.
- Ancho útil `U = W - 2P`; separación de contenido a cada borde de `.app-main`: `G = (A-W)/2 + P`. Desviación de W, P y U respecto a fórmula ≤2px; diferencia de separaciones izquierda/derecha ≤2px.
- El borde del primer bloque de contenido debe coincidir con el inicio útil del contenedor ±2px; no se mide la primera letra de texto ni un elemento deliberadamente indentado.

| Viewport nominal | A nominal | W | U | Separación útil izquierda/derecha |
|---|---:|---:|---:|---:|
| 375×812 | 375 | 375 | 343 | 16 / 16 |
| 768×1024 | 768 | 768 | 736 | 16 / 16 |
| 1280×800 | 1040 | 1040 | 984 | 28 / 28 |
| 1440×900 | 1200 | 1120 | 1064 | 68 / 68 |

Los valores nominales presuponen scrollbar sin reserva lateral. La aceptación usa `A` y `clientWidth` medidos, no fuerza cifras incompatibles con scrollbar clásico. Registrar `innerWidth`, `clientWidth`, devicePixelRatio, zoom y `matchMedia('(max-width:800px)')` para no confundir tamaño de ventana con viewport.

### Controles C, scroll S y chat H

- Scroll interno permitido: `.dash-nav-scroll-area`, `.prep-chart-wrap`, `.projection-table-wrap`; validar una gráfica realmente poblada con fixture. Preservar min-width de gráfica cuando sea necesario para legibilidad.

# ADR-003: Contenedor dashboard fluido y centrado con límite de lectura

- Estado: propuesto
- Fecha: 2026-10-16
- Task: T-0021
- Spec: SPEC-002

## Contexto

Tri-Coach reserva 240px de navegación en escritorio y limita `main` a 880px sin centrado. El usuario reporta una distribución excesivamente a la izquierda en Safari. El chat usa un layout independiente. Es necesario corregir presentación sin alterar dominio ni datos, con evidencia del navegador real.

## Decisión

Proponer un contenedor exclusivo del dashboard a 100% del área disponible, máximo 1120px, centrado, con padding lateral 28px en escritorio y 16px hasta 800px. Preservar sidebar y disposición por rol del chat. Verificar la geometría definida en SPEC-002 con fixtures locales y Safari real. No crear componentes, endpoints, dependencias ni migraciones.

## Alternativas

Centrar a 880px es más conservador pero utiliza menos ancho; ancho ilimitado sacrifica el límite de lectura; no cambiar conserva el defecto. Se prefiere el límite de 1120px con costo pequeño de validar el nuevo ancho útil. El humano aún no ha aprobado esta decisión.

## Consecuencias

El dashboard amplía su área útil hasta el límite acordado; reglas globales de `main` deben quedar acotadas para evitar efectos cruzados. Aumenta la matriz de pruebas respecto a una edición CSS aislada. La arquitectura permanece bajo ADR-002, sin dependencia inversa ni cambio de excepción MVVM. Rollback de fuente reversible y publicación exclusivamente humana. El número ADR se confirmará libre antes de materializar.
